# Decisions

The settled choices behind superagent. Each entry says what was decided, why, and where it came from.

- **you**: your answer in our discussion.
- **proposed**: my technical recommendation. Open to change until M0 starts. Most are backed by a spike (verified by running code).

Details and evidence: [api-plan.md](api-plan.md), [notes/mastra-1.74.md](notes/mastra-1.74.md), [vision/superagent-architecture.html](vision/superagent-architecture.html).

## Organization

| ID | Decision | Why | Origin |
|---|---|---|---|
| D14 | Agent and department definitions live in our own versioned tables. They compile into runtime Mastra `Agent`s, hot-swapped with `removeAgent` + `addAgent`. Mastra Editor isn't used. | Your call. Also hedges against features moving into EE. Spike-verified, including subagent edits reaching the lead without a rebuild. | you + spike |
| D15 | The chief reaches departments through task threads plus signals (our dispatch module). Leads reach their specialists through Mastra's built-in subagent delegation. | The chief never blocks, each task keeps its thread, and leads keep their own background budget. | built in M3 |
| D16 | The task ledger, phases, events and the decisions outbox are ours, modelled on Mastra Factory. | Mastra has no board or task entity. | built in M3; owner decisions in M5 (D32) |
| D24 | A lead's team is its department's active specialists, resolved per request. Specialists receive only the lead's delegation prompt, not the lead's system prompt or history. One active lead per department (enforced by a partial unique index). | No team lists to maintain: adding, editing or archiving a specialist changes the team on the next run. Specialists get a clean, self-contained task. | built in M2 |
| D25 | Tools are a code-defined catalog (`core`, `web` packs); definitions grant tools by key. The web pack uses the self-hosted SearXNG and Crawl4AI services, and refuses internal and private addresses. | New capabilities ship as code or, from M8, as plugins. Web content is untrusted, so a prompt-injected agent must not reach Postgres, the API, cloud metadata or the tailnet. | built in M2 |
| D26 | The ledger: tasks, an append-only event log (its sequence is the SSE event id) and artifacts. A phase machine says who may move a task where: the owner sends work, accepts, reopens and cancels; the lead reports progress and outcomes but never closes a task (done goes to review unless the department auto-closes); the server dispatches and flags stalled runs. | Every change is one locked read-modify-write plus its event, so the board, the history and the live stream always agree. Review keeps the owner in charge of what counts as done. | built in M3 |
| D27 | Each task has its own memory thread (`task:<id>`, resource `dept:<slug>`). New work starts a fresh lead run on that thread, or waits for the lead's current turn to end; a steered message joins the running turn, and one that Mastra strands is reclaimed and re-sent. The chief hears reports as notification signals on its own thread (`chief:main`). While the lead has a task, a supervisor watches the thread: once it goes idle with nothing left to send and no report, the task is flagged as waiting. So is every task interrupted by a restart. | Fresh runs avoid a 1.74 race where a wake sent just as a run ends is never processed. Deciding on the idle thread, not on one run's end, covers follow-up runs and late messages, so nothing sits "in progress" silently: every stop either reports or reaches the owner through the chief. | built in M3 |
| D28 | Live updates: `GET /v1/events` (SSE) with Last-Event-ID replay from the event log, fed by an in-process event bus (D23). A client that missed more than 5000 events gets a `reset` event and reloads the board. An advisory lock keeps event commit order equal to seq order. | One stream for every client. Reconnects catch up exactly, and nothing is skipped when two tasks change at the same moment. | built in M3 |
| D29 | Knowledge: uploaded files go to SeaweedFS (S3 API, on its own network with the API); their text is read in a worker thread (memory limit, timeout, page cap, text budget), split into overlapping passages and indexed with Postgres full-text search (`simple` configuration). Queries are tokenised by Postgres too, any word may match, common words dropped. Agents search their department's documents plus the shared ones with `knowledge_search`. Embedding-based search joins once an `embedding` model role exists. | Works today without an embedding model (the owner's provider has none yet) and keeps everything in Postgres. A hostile file can only exhaust the worker. Department scoping keeps results relevant. | built in M4 |
| D30 | Memory: the owner profile and department notes live in our tables, written only through `MemoryService` (validated, merged, serialized). The chief updates the profile with `update_owner_profile`, leads append to their department's notes with `save_department_note`, and the owner edits both over `/v1`. Input processors put the profile in every agent's context (read-only for departments) and the notes in the lead's. Each profile has its own Memory: observational memory compresses long threads with the `fast` model (the `default` one while the fast one can't be used) and lets calls without a thread through. | The owner tells the chief once and every department knows; a rule learned in one task applies to the next. One write path avoids Mastra working memory's unvalidated writes, unlocked merges and full replaces. Compression keeps long task threads within the model's window. | built in M4 |
| D31 | Schedules are ours: a `schedules` table and a ticker in the API process that claims due rows with a compare-and-set on `next_fire_at`. Each fire creates a task (source `schedule`) in the schedule's department and dispatches it to the lead like any other work; the task's idempotency key (`schedule:<id>:<due time>`) makes each due time fire once, and a fire whose task couldn't be made is put back for the next tick. Fires missed while the server was down are caught up once, at the first tick, and the brief says how many were skipped. A schedule's timezone is the owner's when it is created unless it names one (it doesn't follow later changes). Fires stay at least 5 minutes apart: saving checks the next 50 fires, and each fire schedules the next one 5 minutes on at the earliest. A department has at most 20 active schedules. Leads change only the schedules an agent set up, and may pause but not resume them or run them by hand; the chief runs a schedule by hand at most once per interval. A department without a lead keeps the task in its inbox, and attention shows it; archiving a department pauses its schedules. | Mastra's scheduler drops fires that come due at boot, deletes a schedule whose agent or thread is missing (replacing a lead would lose its schedules), can't move a schedule to another agent, and reports a fire as finished once it is accepted. Firing tasks through dispatch reuses the supervised path, so a scheduled run that stalls reaches the owner like any other. The limits keep a lead that read something malicious from turning schedules into a flood of work. | built in M5 |
| D32 | Attention is computed on each request from the ledger and Mastra's storage, never stored: tool calls waiting for approval (each lead's suspended runs), questions (a lead reported `blocked`), tasks that stopped, results to review, and setup problems (no usable default or fast model, no object storage, schedules for a department without a lead). The owner approves or declines a call over `/v1/attention`. Every decision on a call, the owner's and the decline a cancel makes, is written to the decisions log under one lock before Mastra hears of it, and removed if Mastra refuses it; a retry with the same idempotency key returns the first outcome, and a call is offered only once its task is parked and never after a decision. A gated call moves its task to `waiting` and tells the chief; until the decision, the task takes no new work (409 `approval_pending`), checked under the same lock. Cancelling a task declines what it was waiting for and stops the turn the decline resumes. A lead can't be archived while calls wait for it or its runs are going. | Nothing to keep in sync, and approvals survive restarts because Mastra persists suspended runs. Mastra lists a decided call as suspended until its resumed run ends, and resuming it again runs the tool twice: our log is what says a call is decided. One lock keeps a decision and a fresh run from both starting on a thread, which Mastra allows. Deciding a call needs its agent registered. | built in M5 |
| D33 | Each task gets a folder (`tasks/<id>` in the `superagent-workspaces` volume) and, once an agent works in it, a sandbox container that mounts only that folder, at `/workspace`. Sandboxes run as a non-root user with no capabilities, a read-only root and a private `/tmp`, no network at all, and limits on memory, CPU and processes, from an allowlisted image only (`dev`: Node, Python, git), never pulled. The runner (`apps/runner`) is the only Docker client (D10): it creates, runs and reaps them behind a token, on a network only the API joins. Agents granted `files` or `shell` get Mastra's workspace tools inside a task; a lead hands its task to the specialists it delegates to. Every file operation runs inside the task's container. Idle sandboxes stop after 15 minutes and are removed after 7 days stopped; their files stay, and the next command brings the sandbox back. Limits keep one task from hurting the rest: no file over 2 GiB, no commands or writes while the disk has under 2 GiB free, at most 8 sandboxes running (the least recently used idle one is stopped first), file operations on regular files only and under 30 seconds, and a command nothing can kill (every process slot taken) costs its sandbox a restart. The owner reads a task's files over `/v1` without starting work. | Mastra's `LocalFilesystem` follows symlinks a sandbox can plant (writes escaped its root in a spike), so files are only ever touched inside the container. Without a network, code that read something malicious can't reach Postgres, the tailnet or the internet; the price is no package installs, so the image carries the usual tools. | built in M6 |
| D34 | Agents browse in real browsers: one Chromium container per task, from our image, started by the runner as a non-root user with no capabilities, a read-only root, limits, and a seccomp profile that lets Chromium sandbox its renderers. Browsers sit on the internal `superagent-browsers` network, whose only way out is the egress proxy (`apps/egress`): it resolves each name itself and dials only public addresses, on ports 80 and 443. DevTools listens on the container's loopback only; the API reaches it through the runner, which relays each connection into the container (`docker exec socat`) behind a single-use ticket. Each browser has its own AgentBrowser in the API. Agents granted `browser` get its tools inside a task, routed by the task (never by the thread, which a specialist's model can set); `goto` checks the URL first. A browser closes after 10 minutes unused, when its task ends, or when an agent or the owner closes it. Identities are named, signed-in profiles (a volume each), used by one browser at a time: a task's browser holds the identity's lock, a lease renewed while it is open, and another task needing it waits (attention shows it). The owner signs an identity in through a sign-in session and its live view, so passwords never reach a model. The live view (a WebSocket under `/v1`, behind the token) streams frames; the owner takes over to click, type or navigate while agents' browser calls wait. `fetch_page` falls back to a shared reader browser, a fresh context per page, when the page service can't read a page. | Agents need JavaScript sites and sign-ins. Nothing in a browser container listens on a network, so a hostile page reaches neither the API nor other browsers, and the proxy keeps it off Postgres, the host's ports, the tailnet and cloud metadata, whatever its scripts or redirects do. Mastra's own live-view route has no auth, so we never mount it. One AgentBrowser per browser keeps one task's drop or close from touching another's (AgentBrowser tracks a single current thread). A profile used by two browsers at once corrupts, and cookies are only saved when Chromium stops on SIGINT. Crawl4AI stays where it is: it already runs its browser through its own pinning proxy that refuses non-public addresses. | built in M7 |
| D35 | Secrets live in our vault: a `secrets` table, each value sealed with SecretBox and bound to its id, names in upper snake case. Values are never returned or logged. MCP servers' headers and environment refer to secrets by name (`{ "secret": "NAME" }`); a secret in use can't be deleted, and rotating one reconnects the servers using it. Values a plugin's install makes from its inputs (its servers' environment and headers) become secrets it owns, written with the install and named with a hash of it, so no plugin can take or replace another's. They go with the plugin, unless a server of another origin uses one: that one stays, owned by nobody. A server whose secret is missing is marked failed; it never stops the API from starting. | Credentials for capabilities need one place, encrypted at rest like provider keys, that agents can't read. | built in M8 |
| D36 | MCP servers: one `@mastra/mcp` client per server revision. A server's tools are listed once and kept in our table, and agents get wrapper tools named `<slug>_<tool>`, from their version's and their department's grants (`{ server, tools?, requireApproval }`). Grants carry the allowlist and approvals (D32). Slugs have no underscore and may not be the first word of a built-in tool's name (`web`, `browser`, `update`...), so no MCP tool can take a built-in's name; built-ins also win any clash when an agent is compiled. Remote servers speak Streamable HTTP and reach public addresses only, every redirect checked and kept to the same origin, unless the owner marks one private-network. Servers' instructions never reach a model. stdio servers come with plugins: one container per plugin, from our `mcp` image (Node, Python, uv), started by the runner like sandboxes, with its packages installed into its volume at install time, pinned, scripts off, through the egress proxy. The runner execs each server and relays its stdio as a Streamable HTTP endpoint, so nothing in the container listens; a message over 8 MiB stops the server. Each plugin's container sits on an internal network of its own, which the runner has the egress proxy join (found on the `superagent-mcp` network): its only exit, and no way to other plugins. Or it has no network. A server's secrets reach its process, not its container. A plugin's servers share its container and user, so they can read each other's environment: a plugin is trusted as a whole, never across plugins. Idle containers stop after 10 minutes, and their networks go with them. An uninstalled plugin's package is refused by the runner from then on, and leftovers of plugins that are gone are removed when the API starts. Retries: a call is sent again only after an HTTP 404 (a lost session: it never reached the server), never after a tool's error. | Remote and local servers look the same to agents, and approvals and allowlists stay ours. An MCP gateway container would need the Docker socket (it starts servers with `docker run`), which only the runner may hold (D10); third-party bridges would add a listener inside untrusted code. Installing at install time, not at every start, keeps versions pinned and runs no install scripts. | built in M8 |
| D37 | Skills are pinned files in the database, imported with plugins and validated on import (an invalid one is skipped and listed). Agents and departments attach them by `<plugin>/<skill>`, or by plugin name for all of a plugin's skills. Mastra reads them through our read-only `SkillSource`, per request, so attaching or detaching applies on the next run: the catalog goes into the prompt, and `skill`, `skill_read` and `skill_search` read them. Skills' scripts don't run anywhere yet: sandboxes have no network and the `dev` image lacks most skills' tools. | Knowledge and procedures without code. Serving files from our store keeps them away from the sandbox-writable task folder that Mastra would otherwise read skills from. | built in M8 |
| D38 | Plugins come from GitHub, pinned to a commit when previewed, or from a `.tar.gz` URL with its sha256. The API reads the manifests at that commit, then downloads the archive with every hop checked and unpacks it in a worker as it streams. Only the plugin's files are kept, in memory and then in Postgres. Regular files only, no paths out, with caps on what streams past and what is kept. Formats, detected in this order: Agent Plugins 1.0, `.codex-plugin`, `.claude-plugin`, plain skill folders. Their skills and MCP servers are installed; commands, agents, hooks and other components are listed and ignored. A preview shows everything first, including the values the plugin needs. An install creates rows the plugin owns, and an uninstall removes all of them, after taking its skills and servers away from agents (new versions) and departments. | One install path for the plugin ecosystems, with nothing fetched or run unpinned, and a clean uninstall. | built in M8 |
| D39 | Every agent run is traced with `@mastra/observability` 1.18.3 into Mastra's storage (`mastra.mastra_ai_spans`), streamed chunks left out. A task's runs, and the approval resumes that continue them, carry `tracingOptions` from `DispatchService`: tags `task:<id>` and `dept:<slug>`, and metadata `taskId`, `departmentId`, `department`, which every span of the trace inherits (specialists', tools', memory's). Studio's Traces page reads them. Traces hold whole prompts and outputs, so they are pruned after `TRACE_RETENTION_DAYS` (default 30; Mastra never prunes on its own) and left out of backups. Before Mastra shuts down, tracing is flushed (Mastra closes its storage first). | One trace per task across its lead and specialists, without our own instrumentation. Metadata, not tags, reaches child spans. | built in M9 |
| D40 | Tokens and cost come from the traces: our exporter writes one `usage_events` row per `MODEL_INFERENCE` span (one model request; the generation and step spans above it repeat its tokens), with the task and department from the inherited metadata (or a task thread), the agent, provider and model, and the tokens (input, cached input, output, reasoning). Each row is priced when written, from `model_prices` (USD per million tokens, input, cached input and output, set by the owner per provider model); a model without a price counts tokens at no cost, and a new price doesn't reprice old calls. Tasks carry their totals (`usage` on every task, board card and list), and `GET /v1/usage` groups them by department, task, agent, model or day. | Mastra's bundled price table can't price arbitrary OpenAI-compatible models, and its metrics need storage we don't run. One row per request keeps a turn that switches models priced right. | built in M9 |
| D41 | Backups: `scripts/backup.sh` writes a Postgres dump (custom format, zstd; traces' rows left out) with a manifest of every table's row count taken in the dump's own snapshot, tarballs of the task files and of plugins' MCP volumes (with their labels), and an rclone mirror of the documents bucket (deleted files kept apart, by date). A backup is written as `.partial` and renamed once complete, one runs at a time, the backups folder is readable by its owner only, and the last `BACKUP_KEEP` stay. `scripts/restore-drill.sh` restores a backup into throwaway containers on an internal network, and removes them with their volumes: the row counts must match the manifest; the API must get ready on it, and the API's boot check must find that the current encryption key opens its provider keys and secrets; every document's file must be in the backup, and the mirror must copy into a fresh SeaweedFS with no difference; the archives must read back whole. CI keeps a document, then runs both against the packaged stack. `.env` is backed up by hand, elsewhere; browser identities are not backed up. | A backup is only as good as its last restore. Counting in the dump's snapshot makes the drill exact even while the stack works, and a key check that doesn't depend on which secrets exist makes a wrong `.env` impossible to miss. | built in M9 |
| D42 | The server runs prebuilt images: `scripts/release.sh <version> --save` builds and tags them and saves them to one tarball, loaded on the server with `docker load`. `compose.prod.yaml` overrides compose.yaml there: our images by `SUPERAGENT_VERSION`, never built or pulled; memory, CPU and process limits and rotated logs on every service; only the API published, on loopback, for `tailscale serve` (HTTPS on the tailnet). Docker runs rootless, with cgroup delegation; the runner refuses to create containers where the daemon would ignore their limits. CI runs its stack this way. Upgrades follow `docs/runbooks/upgrade.md`: back up, load, start, check. | A server that builds nothing has nothing to compile or pull at deploy time, and runs exactly what CI tested. No registry: publishing images is a separate choice. | built in M9 |

## Server and code

| ID | Decision | Why | Origin |

| D17 | Our own Hono app, with Mastra mounted on `/api` through `@mastra/hono`. Our control-plane routes live on `/v1`, behind the same auth. We don't use `mastra build`. | We control boot order (migrations before listen) and shutdown (SSE drain), get native HTTP status codes, and can test in-process with `app.request()`. Mastra reserves `/api` for itself. | proposed, verified |
| D18 | TypeScript strict, ESM, zod 4, Node 24 LTS (22.22+ minimum). pnpm workspaces; tsdown for builds; `tsx watch` in dev; Biome for lint and format. | Matches Mastra's toolchain. zod 4 is what core uses. | proposed |
| D19 | Drizzle ORM 0.45 for the `app` schema, with migrations applied at boot. One `pg.Pool` shared with Mastra's `PostgresStore`. | Typed SQL, generated migrations, and `schemaFilter` keeps drizzle-kit away from Mastra's tables. Spike-verified. | proposed, verified |
| D20 | Auth: our `ApiTokenAuth`, a Mastra auth provider that checks hashed tokens in `app.api_tokens`. A bootstrap admin token comes from env. Only the admin token can create, list or revoke tokens; a device token can only revoke itself. Studio gets its own `SimpleAuth` token. We don't use `mapUserToResourceId`. | Revocable device tokens for future clients, without EE. A stolen device token can't mint replacements, so revoking it locks the thief out. Spike-verified. | proposed, verified |
| D21 | Tests: Vitest. Agent flows use scripted mock models (`MockLanguageModelV4` from `ai/test`) with in-memory LibSQL. Integration tests use Testcontainers Postgres. A live suite runs against your LLM server behind a flag. | Deterministic orchestration tests without paying for tokens. Spike-verified on this PC. | proposed, verified |
| D22 | Experimental Mastra APIs (signals, notifications, thread subscriptions) are called only through our own modules. | They're marked `@experimental` in 1.74, so a breaking change touches one file. | proposed |
| D23 | A single API process, with Mastra workers running in-process. Split workers and Valkey only if load ever needs it. | Simplest setup that is fully supported. | proposed |
