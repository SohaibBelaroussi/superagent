01The short answer

Mastra can carry this system. It supplies the agent runtime. We build the control plane: the parts that turn a set of agents into an organization you can watch and steer.

  • RuntimeMastra covers agents, subagents, background tasks, runtime-created schedules, memory, approvals, Docker sandboxes, browser control, MCP and skills. All of this is Apache-2.0.
  • We buildThe task ledger and board, the department model, a capability catalog with a plugin installer, a small "runner" service that owns Docker, and push notifications. Mastra has no Kanban or unified task entity. Its "task tools" are a per-thread to-do list.
  • UI-built agentsPossible for free. Mastra Editor (Apache-2.0) stores versioned agents, skills and MCP configs in the database and exposes them over REST, so our own web app can create departments without redeploying. Mastra's ready-made Agent Builder UI is Enterprise-licensed and needs a paid key for real use, so we skip it.
  • HierarchyThe chief should hand work to department leads through persistent task threads and signals, not through Mastra's built-in subagent call. Leads then use the built-in call for their own specialists. This sidesteps Mastra's one-level limit on background delegation.
  • PluginsThe cross-vendor Agent Plugins 1.0 spec (the format Codex uses) bundles exactly two things: skills and MCP servers. Both map cleanly onto Mastra. Hooks and vendor app connectors don't, and Mastra has no plugin system of its own.
  • Main risksWhatever can create containers is root-equivalent unless Docker is isolated. Mastra 1.74's live browser stream appears to skip auth. LinkedIn's terms ban the automation you described. Several needed features are beta or pre-1.0.

04Departments

Three layers. One chief of staff you talk to. One lead per department, which owns that department's work and memory. Specialists and fixed workflows under each lead. You talk to the chief, and you can open any department's task thread and talk to the lead directly.

Why the chief does not use built-in delegation

Mastra's subagent call (agents: {}) is fine inside a department and wrong between the chief and a department:

  • Every call opens a fresh thread, so "also add tests" on yesterday's task would start from nothing.
  • The work runs inside the chief's own run, so the chief is busy until the department finishes.
  • Only one level of background delegation is allowed. If the chief used it, a lead could not background its own specialists.

Instead, each lead runs as the root agent of a persistent task:<id> thread. It gets the full background budget for its specialists. Mastra Factory, Mastra's own work-board product, uses the same pattern: its supervisor reaches worker sessions by sending messages, not by delegating.

How the chief keeps you up to date

  1. Ledger first. Cheap tools that read rows: overview, inspect task, what needs attention, health checks. The health checks are plain queries with no model calls, like "running for six hours with no events".
  2. Transcripts and memory next, only when the rows don't explain a card. It reads the task thread or the department's memory through the memory API.
  3. Steering last. It queues a message into the task thread, tagged as coming from the chief, so the lead sees who is asking.

UI-built departments can join the hierarchy

A stored agent's definition has an agents field, so a department created in our UI can list its specialists. There is a catch. Editor resolves those references against agents already loaded, and silently drops unknown ones. The server therefore has to load stored agents leaves-first at boot. This needs a spike to confirm (see Still unverified).

05Tasks and the board

The ledger is the single source of truth. Mastra's own records feed it: background-task events, the lead's checklist, goal judgements, approval suspensions and schedule triggers. Each card is a task thread, so opening a card opens the conversation where the work is happening.

What a card shows

  • Department, the agent in the seat, phase and how long it has been there.
  • The lead's checklist, taken from Mastra's per-thread task tools. That is the right job for them: a checklist inside a card, not the board itself.
  • Artifacts: reports, rendered videos, pull requests, screenshots, stored in S3 and opened through presigned links.
  • Pending approvals, with approve and decline buttons.
  • Cost and tokens. Each task runs with tracing tags (task:<id>, dept:<id>), and the card sums the metrics for that tag.

Live updates

Every ledger write appends a task event with a sequence number and publishes a small change hint on Mastra's pub/sub. A custom SSE route forwards the hints, and clients refetch the cards that changed. Reconnecting clients send the last sequence number they saw and get the gap replayed. This is how Factory does it. Mastra's background tasks do have read-only routes (GET /background-tasks and a completion stream), which we bridge into the ledger. There is no cancel route, so cancelling goes through our own API.

Schedules

Agents create schedules at runtime through mastra.schedules.create. A schedule fires into the department's inbox thread, and the lead turns each firing into tasks. Two limits matter. The scheduler is a polling loop inside the server, so the host must stay up. Fires missed during downtime are not replayed, so we should add a check on boot that runs each overdue schedule once.

Approvals

Gated tools (send, apply, publish, push, pay) use requireApproval or suspend mid-run. Suspended runs are stored, and listSuspendedRuns recovers them after a restart. The card moves to "Waiting on you", the attention inbox lists it, and your phone gets a push. We avoid Mastra's AgentController for this, because its sessions and pending approvals live only in memory.

License

The Mastra Enterprise License v2.0 (effective 22 Sept 2026) allows free use only for development and testing, in an environment that handles no real data. Anything else needs a signed agreement and a license key, with no personal-use exception. EE features still work in development mode without a key, but that is a technical behavior, not permission. Your daily assistant counts as production use. We should block every */ee import in CI.

Mastra can also reclassify features as Enterprise at any time. To hedge, we keep our own agent-definition tables as the source of truth and compile them into Editor records. If Editor ever moves behind the license, we swap that compile step for plain new Agent() plus mastra.addAgent, and the UI does not change.

The capability catalog

Everything an agent can be given appears in one catalog that our server exposes to both apps. Studio is not involved.

Built into our server

  • Workspace files, shell, code search
  • Browser (per task, or a named profile)
  • Research: search, fetch, crawl
  • Code mode for parallel tool fan-out
  • Ledger, schedule and notify tools
  • Sandbox images (base dev, Python, HyperFrames)

Added at runtime

  • MCP servers (HTTP, or stdio run in containers)
  • Skills (Agent Skills format, versioned in Editor)
  • Plugins (bundles of skills and MCP servers)
  • Models and memory profiles
  • Browser identities (logged-in profiles)
  • Secrets, scoped to one plugin or agent

Large agents get Mastra's tool-search and skill-search processors, which expose search and load tools instead of putting every schema in the prompt. The UI can't write new code tools, and Editor says so. New abilities arrive as MCP servers, skills with scripts that run in the sandbox, or plugins.

The plugin format

The Agent Plugins spec (agent-plugins.org, v1.0, steering committee from Amazon, Cursor, Microsoft, OpenAI and Vercel) is the cross-vendor format. Codex has used it since v0.146 and also reads Claude Code marketplaces. A plugin is a folder with:

  • plugin.json: name, version, author, license, and vendor extensions under reverse-domain keys.
  • skills/*/SKILL.md: Agent Skills, the same format Mastra reads.
  • mcp.json: stdio or streamable-HTTP MCP servers.

Version 1 has no trust model, permissions, signing or secrets, so our installer supplies those. Claude Code plugins carry more component types: subagents, commands, hooks, LSP servers, themes.

Installing a plugin

  1. Fetch and pin. From git, npm or an archive. Pin the commit, unpack read-only to /plugins/<name>/<version>, create its data volume.
  2. Validate. Check plugin.json against Agent Plugins 1.0. Fall back to .codex-plugin or .claude-plugin manifests.
  3. Review. Show what it contains: skills, MCP commands, hosts it contacts, secrets it needs. Nothing runs before you approve.
  4. Secrets. Collect them in our form. They are injected only into that plugin's container and never written to the manifest or the stored MCP config.
  5. Map components onto Mastra (table below).
  6. Enable per agent or per department, with an allowlist of tools and approval on anything that writes.

07Memory

Mastra scopes memory by resource (an owner id) and thread (one conversation). A thread belongs to one resource for life. Working memory is a structured note with one slot per memory configuration. Observational memory compresses long threads in the background. Semantic recall searches past messages with embeddings. The model below gives each layer of the organization its own scope.

Things that shape this design

  • One working-memory slot per agent. Your profile can't also live in every department's working memory, so it is injected read-only instead.
  • No access control inside memory. Any code can read any resource. The boundaries are enforced by which tools each agent gets, which suits one user. Don't set Mastra's resource-id lock (MASTRA_RESOURCE_ID_KEY): it would pin every call to a single resource.
  • UI-built agents reference memory by id. Inline memory configs in stored agents leave out working memory. So we register a few memory profiles in code (chief, lead, specialist) and the UI picks one.
  • Observational memory costs model calls. A background model writes the observations. Its default is a hosted Gemini model, and it can point at a local model instead.
  • Resource-scoped observational memory is deprecated. Use thread scope plus the recall tool, as in the table.

08Sandboxes, browsers, research

Sandboxes

DockerSandbox is one long-lived container per sandbox. Commands run through docker exec, and a container is found again by its label, so a task resumes in the same container. A resolver keyed on the task gives one sandbox per task. Mastra only stops containers and never deletes them, so the runner needs a reaper.

  • Workspace. One named volume with tasks/<id> and projects/<id>. Each sandbox mounts only its subpath (Docker Engine 26+). The server creates the folder first, because Docker won't.
  • Hardening. Drop all capabilities, no-new-privileges, memory and process limits, tmpfs for /tmp and /dev/shm, no secrets, an internal-only network or an egress allowlist.
  • Gaps in 0.9. No options for user, runtime or shared-memory size. We bake a non-root user into each image and set a stronger runtime (gVisor) as the daemon default.
Docker access is root access

Mounting the Docker socket, even read-only, gives root on the host. Socket proxies filter by API section but don't inspect request bodies, so anything allowed to create containers can create a privileged one. The design therefore gives Docker access only to the runner, which runs against a rootless Docker daemon and enforces an image allowlist, mounts, networks and time limits. On the Mastra side this means a custom sandbox class that calls the runner. Docker Desktop on Windows supports neither rootless mode nor Sysbox, which is one reason to run the system on a Linux host.

Browsers

Every Mastra browser provider can attach to a remote Chromium over CDP. AgentBrowser fits best: it reads a deterministic accessibility snapshot and acts on element references, with no extra model calls. That also makes it friendlier to local models. Stagehand needs its own model for each action.

  • One browser container per task. A plain cdpUrl forces one shared browser, so we write a small thread manager that asks the runner for a container per task. FirecrawlBrowser's source is the template. For images, use Chromium with a socat proxy, or Steel (Apache-2.0). Avoid browserless, which is SSPL-licensed.
  • Logged-in identities. One volume per identity, used as the Chrome profile directory. Chrome allows only one process per profile, so the runner holds a lock and queues that identity's tasks. Since Chrome 136, remote debugging requires a non-default profile directory.
  • Watching and taking over. Mastra streams a live screencast over a WebSocket (/browser/:agentId/stream) and accepts mouse and keyboard input on it. Our apps can speak that protocol, so you can type a 2FA code from your phone. The frames are JPEGs: fine for typing and clicking, poor for drag puzzles.
Security flag

In Mastra 1.74 the browser stream routes appear to be registered before the auth middleware, with no auth check in the handler. Until that's verified or fixed, caddy must require auth on /browser/*.

Research without paid APIs

Mastra has no SearXNG integration, so search and fetch become two small custom tools:

  • SearXNG (AGPL) for search. Enable JSON output and turn off the rate limiter on the private instance. Upstream engines will sometimes block a single IP. Spread queries across many engines, prefer API-backed ones (Wikipedia, arXiv, GitHub, StackExchange), cache results and back off.
  • Crawl4AI (Apache-2.0 with an attribution clause) turns pages into markdown in one container. Self-hosted Firecrawl needs five services and lacks browser actions.
  • Our browser containers handle JavaScript-heavy or logged-in pages.

The research department: a lead that plans and judges completeness (a goal with a judge model, "keep going until the question is answered"), searchers fanned out through code mode, a reader that extracts and cites, and a writer. Sources are saved to the task workspace and indexed for search, and the report goes to S3.

09Data, models, observability

Database: Postgres with pgvector

The Postgres adapter implements every Mastra storage domain this design uses: memory, background tasks, schedules, notifications, Editor records, observability. pgvector covers semantic recall and document search. Our ledger lives in its own schema in the same database, where row locks (SKIP LOCKED), advisory locks and LISTEN/NOTIFY serve the queue and the browser-profile locks. LibSQL is a single-writer file. It is fine for development and weak once background tasks, the scheduler and API requests all write at the same time.

Object storage: SeaweedFS

MinIO's community edition is effectively gone. The admin console was removed in May 2025, images stopped in October 2025, and the repository was archived in February 2026. SeaweedFS (Apache-2.0) runs as one container with versioning and object lock. Garage (AGPL) is lighter but has no versioning. RustFS reached 1.0 only in September 2026. S3 holds artifacts, Editor blobs and backups. Task workspaces stay on the volume, because Docker sandboxes can't mount S3.

Valkey: only when you split processes

A single server process needs no Redis-like service: Mastra's in-process pub/sub and stream cache are enough. Valkey (BSD) becomes necessary only if workers run separately from the API.

Models

"No subscriptions" leaves two paths, and the choice is yours (see Decisions):

  • Pay-per-use API keys through Mastra's model router, with fallback chains. No monthly fee, but it is still a third-party service.
  • Local models through any OpenAI-compatible server (Ollama, llama.cpp, vLLM) in Docker. Agents that call tools reliably want roughly 30B-class models or larger. 24 GB of VRAM runs 20–30B models at 4-bit with modest context. CPU-only is practical just for embeddings. Watch out for ollama-cloud in Mastra's provider list: it is a paid hosted service, not local.

A practical mix is API models for the chief and leads, and local models for embeddings, the observational-memory writer and simple classification.

Observability

Mastra traces every run and estimates cost from a built-in price table. Metrics need an analytics-capable store, such as Postgres with its observability domain or DuckDB. LibSQL has no metrics support. Traces filter by tags and metadata, which gives per-card cost.

10API and clients

The API surface

Built in: agents (49 routes, including streaming, wake-a-thread messaging, live thread subscriptions and approvals), memory (19), workflows (26), schedules, background tasks (read-only), stored Editor records (41), workspaces (21), observability (43), MCP and A2A. Our own routes, added with registerApiRoute (authenticated by default, listed in OpenAPI):

  • /board/* for tasks, phases, comments and the event stream.
  • /departments/* and /agents/* definitions, compiled into Editor.
  • /capabilities, /plugins/* and /secrets/*.
  • /attention, the inbox of approvals and blocked tasks.
  • /push/* for device registration.

Streaming

Everything streams over SSE. To watch a department live, the app subscribes to its task thread. Dropped mobile connections can resume from an offset once a caching pub/sub is configured. Browsers' built-in EventSource can't send auth headers, so the apps use fetch-based SSE, which the Mastra client already does.

Auth and network

  • Device tokens with Mastra's SimpleAuth, or expiring JWTs with MastraJwtAuth. Both are free. Better Auth in front of Studio in production falls under EE, so skip it.
  • Keep the server off the public internet. Self-hosted WireGuard or Headscale keeps everything under your control. Tailscale's free tier is easier but is a third-party service.
  • Studio stays available as an admin console behind the same auth.

The apps

Web app

  • Chat with the chief or any lead (assistant-ui or AI SDK UI)
  • Department boards and the CRM-style table view
  • Department and agent builder, capability catalog, plugin installer
  • Attention inbox, live browser view with takeover
  • Schedules, memory viewer, costs

Mobile app

  • Chief chat, attention inbox, approvals
  • Board overview and card detail
  • Browser takeover for logins and 2FA
  • Expo with the AI SDK (expo/fetch transport). The Mastra client accepts a custom fetch, but streaming that way is unverified

Push without paid services

  • First: install the web app as a PWA and use Web Push with self-generated VAPID keys. Free, no account, works on iOS 16.4+ once added to the Home Screen.
  • Native app: the server sends straight to APNs and FCM. Both are free, but iOS needs an Apple Developer account. Expo's push service is a third-party relay we can skip.
  • Android without Google: UnifiedPush, with a self-hosted ntfy as the distributor.

13Decisions for you

These change the design itself, so they need settling before anything else.

  1. Models: pay-per-use API, local GPU, or a mix?

    API keys have no subscription, but they are a third-party service. Fully local needs serious GPU memory for reliable tool calling. A mix is the practical middle.

  2. Where does it run?

    A dedicated Linux box or VPS gives rootless Docker, fast volumes and real uptime for schedules. This Windows PC with Docker Desktop works for development but weakens isolation.

  3. Remote access: self-hosted WireGuard or Headscale, or Tailscale's free tier?

    Self-hosting matches your no-third-party rule. Tailscale is simpler to run.

  4. How far should the LinkedIn agent go?

    Full automation, drafts only, or job search plus external applications only. This decides how much account risk you accept.

  5. Mobile: PWA first or a native Expo app from the start?

    A PWA gets free Web Push and shares the web codebase. Native means better background behavior, plus an Apple Developer account for iOS push.

  6. Agent definitions: our own tables or Mastra Editor's directly?

    Our tables hedge against license changes and keep the UI ours. Editor directly is less code. I recommend our own tables.

14Still unverified

Claims this design leans on that were read from docs or source but not run. Each needs a small spike before committing.

  • Stored departments resolve their stored specialists when loaded leaves-first at boot.
  • The /api/stored/* routes in @mastra/server carry no license check. The guard was seen only on the Builder.
